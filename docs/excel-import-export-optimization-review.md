# Excel 导入导出优化路径与复盘

本文基于当前实现、R7 标准环境测试结果和历史本地基线整理。目标不是罗列功能，而是复盘这个项目如何从“Excel 导入导出演示”逐步演进成具备任务化、对象存储、权限隔离、可恢复和可观测能力的后端样例。

## 1. 当前结论

| 维度 | 当前状态 |
| --- | --- |
| 导入 | 真正异步任务；源文件存 MinIO；EasyExcel 流式解析；2000 行一批；多 worker 暂存；校验后单事务合并正式表 |
| 导出 | 真正异步任务；游标分页；快照上界；单 Sheet；本地临时文件生成后上传 MinIO；下载返回 302 签名 URL |
| 任务中心 | Redis 缓存状态 + MySQL 持久化；支持创建、运行中、成功、失败、取消、重试、过期和分页查询 |
| 文件中心 | 后端上传、秒传、客户端直传、分片上传、断点查询、取消、逻辑删除和签名下载 |
| 权限 | demo 模式兼容本地调试；关闭 demo 后使用 Bearer Token，任务、文件、运行控制按 owner 隔离 |
| 测试 | `mvn test` 40 用例通过；接口扁平化 R7 历史记录为 76 用例 / 72 通过 / 4 失败，F-02 已本地回归修复，脚本已加固导出超限和取消竞态误判 |
| 性能 | 标准环境 1M 导出 3/3 成功，约 23,317 行/s；100k 导入 3/3 成功，约 3,908 行/s |

剩余主要问题：

- F-02 已修复：框架层参数异常统一映射为 400/415，并补充本地回归测试。
- F-09：百万级导入最终合并事务大概率超过 60 秒，需要分块合并或提高事务超时。
- F-11：小规格单机 Docker 曾因导入压力触发 OOM；swap 已缓解 100k 导入，但百万级仍不建议直接执行。

## 2. 演进路径

```text
基础导入导出
    -> 配置外置和建表脚本
    -> MyBatis 批量 upsert
    -> 导入模板和计时日志
    -> 游标分页、快照边界和单 Sheet 导出
    -> 异步导出 + Redis 状态
    -> MinIO 对象存储 + 私有签名下载
    -> 文件上传中心
    -> 统一异步任务中心
    -> 真正异步导入
    -> 全量原子导入
    -> 报表运行控制和通用导出引擎
    -> 权限隔离、统一响应、Flyway、监控和任务恢复
    -> 标准环境压测、复盘和脱敏
```

这条路径的核心顺序是：先保证功能可用，再保证大文件不阻塞请求，再保证失败可恢复，最后补齐生产化边界。

## 3. 导入链路复盘

当前导入流程：

```text
HTTP 上传 Excel
    -> 原始文件上传 MinIO
    -> 创建 IMPORT 异步任务
    -> 后台从 MinIO 读取源文件
    -> EasyExcel 流式解析
    -> 每 2000 行入有界 BlockingQueue
    -> 多个 worker 分批写入 student_import_stage
    -> 扫描暂存表做必填、长度、格式、重复学号校验
    -> 单事务 upsert 到 student_record
    -> 清理暂存数据并更新任务状态
```

这个设计解决了三个问题：

- 内存边界：解析线程只保留当前批次，队列容量有限，数据库慢时会反压解析。
- 失败一致性：正式表只在最终合并时修改，校验失败或合并失败不会污染正式表。
- 任务恢复：源文件在 MinIO，重试和恢复不依赖本机临时目录。

代价也很明确：

- 数据会先写暂存表，再合并正式表，写入链路比直接 upsert 更重。
- 最终合并是单事务，数据量越大，undo/redo、锁持有和事务超时风险越高。
- 多 worker 会增加连接、内存和磁盘 fsync 压力，小规格机器不能只靠加线程提速。

## 4. 导出链路复盘

当前导出流程：

```text
提交导出请求或运行报表控制
    -> 创建 EXPORT 异步任务
    -> 查询当前 snapshotMaxId
    -> 按 id > lastId 且 id <= snapshotMaxId 游标分页
    -> EasyExcel 写本地临时 xlsx
    -> 上传 MinIO
    -> 删除临时文件
    -> 任务成功后返回签名下载 URL
```

关键取舍：

- 游标分页避免 `LIMIT offset` 在大数据量下越来越慢。
- `snapshotMaxId` 是导出边界，不是严格数据库一致性快照；导出期间边界内数据仍可能被更新。
- 当前只导出单 Sheet，是为了保证“导出文件可以直接回导”。超过 Excel 单 Sheet 上限时任务明确失败。
- 下载返回 302 签名 URL，大文件流量不占用 Tomcat 工作线程和应用服务器带宽。

如果未来要支持超过单 Sheet 的导出，有三条路：

- 业务分片导出多个文件。
- 改用 CSV 或压缩包。
- 支持多 Sheet，但导入端也要同步读取多 Sheet，并明确回导语义。

## 5. 任务中心复盘

导入和导出都接入统一异步任务中心后，系统有了统一的任务事实来源：

- MySQL 保存任务记录，便于分页查询、恢复和审计。
- Redis 保存短期状态，提升轮询读取效率。
- 任务状态包含创建、运行、成功、失败、取消、过期。
- 任务 payload/result payload 保存业务参数和结果。
- 恢复协调器通过心跳识别悬挂任务。

这比“Controller 里开线程”可靠得多，但也带来新的边界：

- 恢复协调器的心跳超时不能太长，否则崩溃任务失败落库很慢。
- 重试必须受 `maxRetryCount` 限制，避免坏任务反复压垮服务。
- 取消是尽力而为，已经提交的数据库事务不会自动回滚到取消前状态。

## 6. 标准环境测试复盘

R7 权威结果：

| 项目 | 结果 |
| --- | --- |
| 单元/切片测试 | 40 用例全部通过 |
| 接口扁平化测试 | R7 历史记录 76 用例 / 72 通过 / 4 失败；F-02 已本地修复，环境相关误判脚本已加固 |
| 1M 导出 | 3/3 成功，平均约 43.05 s，约 23,317 行/s |
| 100k 导入 | 3/3 成功，平均约 25.6 s，约 3,908 行/s |
| 1M 导入 | 当前小规格环境不可直接执行，已确认 OOM 和长事务风险 |

几个重要认识：

- “文件已经先上传到 MinIO”只解决应用接收文件和任务恢复问题，不代表导入写库不受机器资源限制。后台解析、暂存、校验和合并仍然发生在应用与数据库之间。
- 当应用和 MySQL 同机时，公网只影响用户上传原始文件；任务处理吞吐主要由服务器内存、CPU、磁盘 fsync 和 MySQL 配置决定。
- 全量原子导入的稳定级别目前是 10 万行级别；百万级需要进一步架构优化。
- 标准环境中导出比导入更稳定，因为导出主要是顺序读和文件写；导入要承担暂存写、校验扫描和最终合并。

## 7. 当前优化路线

### 7.1 近期必须做

1. 给导入增加最大行数或最大文件大小的业务保护，避免小规格环境被误触发百万级导入压垮。
2. 将 `IMPORT_BATCH_SIZE`、`EXPORT_PAGE_SIZE` 从代码常量改为配置，并设置上下限。
3. 调短恢复协调器对失联任务的处理窗口，并限制异常任务反复恢复。

### 7.2 中期优化

1. 分块合并导入结果，降低单事务时长，同时保持可补偿的一致性语义。
2. 增加 CSV 导出或业务拆分导出，解决超过单 Sheet 上限的问题。
3. 增加真实 MySQL、Redis、MinIO 的集成测试环境。
4. 给文件中心补齐类型嗅探、安全扫描和上传审计。

### 7.3 长期演进

1. 将导入/导出 worker 独立成后台服务，Web 节点只负责提交任务。
2. 使用消息队列或数据库任务表调度，降低 JVM 内线程池对可靠性的影响。
3. 建立任务、连接池、MinIO 和机器资源的告警。
4. 增加归档清理策略，避免任务表、文件表、上传任务和对象存储无限增长。

## 8. 复盘总结

这个项目的核心价值不只是“能导入导出 Excel”，而是完整展示了大文件后台任务的工程化闭环：

- 流式处理解决内存问题，但必须配合有界队列和背压。
- 多线程可以提升吞吐，但最终受数据库连接、磁盘和事务限制。
- 全量原子性不是免费的，它用吞吐和长事务风险换正式表一致性。
- 对象存储能解决文件交付和任务恢复，但不能替代数据库写入优化。
- 异步任务中心让长任务可查询、可恢复、可重试，但恢复策略本身也需要限流和告警。
- 文档、测试结果和脱敏同样是交付物，尤其是准备开源或远程部署时。

下一阶段最值得做的是“稳定性护栏”：给导入增加行数上限、分块合并和恢复限流。这样项目从 Demo 走向真实生产样例，会更有说服力。
