# Excel 导入导出优化路径与复盘

本文依据项目从 `edff254` 到 `94696d6` 的提交记录、当前实现和已记录的压测结果整理。目标不是罗列功能，而是说明大文件导入导出从“可用”走到“可运营”的优化顺序、关键取舍和后续方向。

## 1. 优化总览

```text
基础接口可用
    -> 配置外置与模板统一
    -> 导出异步化和任务状态化
    -> 游标分页与单 Sheet 边界
    -> MinIO 对象存储和签名下载
    -> 导入流式解析、批处理和有限重试
    -> 有界队列、多 worker、容量校验
    -> 失败收尾、超时配置校验和专项测试
    -> 压测记录与配置脱敏
```

这条路径体现了一个顺序：先解决正确性和交付方式，再处理吞吐量，最后补齐并发失败场景、观测能力和运维边界。

## 3. 当前实现的关键链路

### 3.1 导入链路

```text
上传 Excel
    -> EasyExcel 流式解析
    -> 当前 2000 行批次
    -> ArrayBlockingQueue 有界队列
    -> 多个 import worker
    -> 暂存表分批写入 + 校验后单事务 upsert
    -> 瞬时数据库异常有限重试
    -> 汇总 imported 和 batchCount
```

当前实现的内存上界主要由“当前解析批次 + 队列中批次 + worker 正在处理的批次”决定，而不是整个文件行数。队列满时，解析线程会等待，形成背压。

当前导入的保护措施包括：

- `IMPORT_MAX_CONCURRENT_TASKS` 通过信号量限制同时执行的导入任务数；
- `IMPORT_WORKER_COUNT * IMPORT_MAX_CONCURRENT_TASKS <= HIKARI_MAXIMUM_POOL_SIZE` 在启动时校验；
- worker 提交失败时取消已提交任务、补齐 Latch 并回收许可；
- worker 失败时清空待处理队列、发送结束信号、取消 Future 并等待收尾；
- 瞬时数据库异常按退避时间有限重试；
- `IMPORT_WORKER_FINISH_WAIT_SECONDS` 与单批事务、重试窗口存在启动期校验。

### 3.2 导出链路

```text
提交导出请求
    -> Redis 写入 QUEUED 任务
    -> exportTaskExecutor 异步执行
    -> 记录 maxId 并按 id 游标查询
    -> EasyExcel 持续写入一个临时 xlsx 文件
    -> 上传 MinIO
    -> 删除临时文件
    -> Redis 更新 SUCCESS
    -> 下载接口返回 MinIO 签名地址 302
```

导出任务在创建时记录 `maxId`，从而排除任务开始后新增且 `id` 更大的数据。它是“导出范围上界”，并不等同于数据库的严格一致性快照：任务执行期间，范围内记录仍可能被更新或删除。若业务要求完全一致的快照，需要使用数据库一致性快照、版本字段或导出快照表。

单 Sheet 的选择是为了支持“导出后直接修改并回导”。当前上限为 Excel 单 Sheet 最大数据行数，超过上限时显式失败，而不是隐式拆分成多个不便回导的 Sheet。

## 4. 性能演进与结论

已记录的 100 万行导入结果如下：

| worker 数 | 批大小 | 耗时 | 吞吐量 | 观察 |
| ---: | ---: | ---: | ---: | --- |
| 4 | 2000 | 42,718 ms | 约 23,400 行/秒 | 可用基线 |
| 6 | 2000 | 33,021 ms | 约 30,283 行/秒 | 相比 4 worker 有收益 |
| 8 | 2000 | 34,265 ms | 约 29,184 行/秒 | 单次结果略慢于 6 worker |
| 16 | 2000 | 15,671 ms | 约 63,812 行/秒 | 当前最快，但需确认连接池、数据库和机器资源充足 |

单任务、单 Sheet 的 100 万行导出耗时为 `63,806 ms`，约 `15,672 行/秒`。

这些结果说明：

1. 多 worker 能提高导入吞吐，但不是线性关系。8 worker 的一次结果慢于 6 worker，不能仅凭线程数判断性能。
2. 16 worker 的结果最好，但不能直接作为所有环境的默认值。它要求更高的数据库连接、CPU、磁盘 IO 和锁竞争承受能力。
3. 当前数据是单次实测，不是严格的基准测试。不同时间的缓存状态、数据库负载、网络、GC 和磁盘状态都会影响结果。
4. 后续应在同一机器、同一数据集、相同数据库数据状态下，每组连续执行至少 3 次，记录中位数、P95、数据库连接数、锁等待、GC 和 CPU/IO，再选定生产配置。

完整原始结果见 [测试记录](excel-import-export-test.md) 和 [压测说明](import-load-test.md)。

## 5. 关键心得总结

### 5.1 流式读取不等于不会 OOM

EasyExcel 流式解析只解决了“不要一次读取整个 Excel”的问题。若解析速度超过数据库写入速度，且批次无限堆积，仍会造成内存增长。因此必须配合有限批次和有界队列，让生产者在队列满时等待。

### 5.2 并发数的上限由最稀缺资源决定

worker 本质上是并发写库单元，最先被耗尽的通常是数据库连接或数据库写入能力，而不是 Java 线程数。代码中的容量校验只能保证不超过 Hikari 上限；生产配置还应预留连接给查询、导出、健康检查和普通业务接口。

推荐按下式规划，而不是刚好占满连接池：

```text
IMPORT_WORKER_COUNT * IMPORT_MAX_CONCURRENT_TASKS
<= HIKARI_MAXIMUM_POOL_SIZE - 预留连接数
```

### 5.3 先定义一致性语义，再谈性能

全量事务回滚适合文件较小、业务必须原子提交的场景，但大文件会带来长事务、undo/redo 压力和锁持有时间。当前采用暂存表策略：解析和暂存分批完成，正式表只在最终校验通过后单事务合并。

这保证了 `student_record` 层面的“要么全部成功，要么全部失败”。后续如果要支持失败行报告、人工修正后续传，可以在暂存表基础上继续增加错误明细文件和任务恢复能力。

### 5.4 异步任务需要状态、存储和清理三件套

导出异步化后，不能只把工作扔进线程池。还需要可查询的任务状态、文件落点、失败状态和过期清理。Redis 承担短期任务状态，MinIO 承担文件交付，生命周期规则负责对象清理，三者共同闭环。

### 5.5 大文件下载应绕开应用服务器

应用服务器转发对象存储文件会占用应用线程、连接和带宽。下载接口返回 MinIO 签名地址后，文件流量直接从对象存储到客户端，应用只负责鉴权和签名。

### 5.6 失败收尾比正常流程更容易出错

并发导入中最危险的不是正常批量写入，而是 worker 提交失败、某个 worker 异常、线程中断和等待超时。提交记录中多次针对 Future、Latch、队列结束信号和许可归还进行修复，说明这部分必须专门写测试，而不能只依赖正常路径压测。

### 5.7 日志需要支持回答性能问题

当前日志包含批次行数、worker 编号、累计处理行数、累计批数和耗时，能定位导入卡在解析、排队还是写库阶段。并发环境中累计计数日志出现先后交错是正常现象，应以最终 `import students finished` 的汇总记录判断结果。

### 5.8 配置和文档也是交付物的一部分

数据库、对象存储、端口和本机路径不应写入仓库。通过环境变量配置，并在 README、测试文档和压测脚本中只使用占位符，才能让项目可迁移、可开源、可安全交接。

## 6. 后续优化路线

### 6.1 近期：建立可重复的性能基线

1. 固定 Excel 文件、数据库数据量、机器规格和 JVM 参数。
2. 分别测试 1、2、4、6、8、12、16 worker，每组至少 3 次。
3. 记录总耗时、中位数、P95、导入成功率、重试次数、数据库活跃连接、锁等待、CPU、磁盘 IO、堆内存和 Full GC。
4. 分开测试“纯导入”“纯导出”“导入与导出同时执行”，不要把不同场景的结果混在一起比较。

### 6.2 中期：增强业务可恢复性

1. 将导入也改为异步任务，上传后返回任务 ID，避免客户端长连接超时。
2. 为导入任务保存进度、失败原因、成功行数和失败行数。
3. 对格式错误、必填字段、重复业务键和业务规则错误生成错误明细文件。
4. 对需要严格原子性的业务使用暂存表和校验后合并策略。

### 6.3 中期：完善导出一致性和容量控制

1. 需要严格快照时，采用事务一致性快照、版本号或导出快照表，而不是只依赖 `maxId`。
2. 将 Redis 进度更新做节流，避免每个分页都产生额外 Redis 写压力。
3. 根据连接池余量限制导入和导出的组合并发，避免导入 worker 占满数据库连接。
4. 对超出单 Sheet 上限的场景提供 CSV、按业务条件拆分，或明确拒绝并给出可操作错误信息。

### 6.4 长期：从接口实现升级为任务平台能力

1. 导入导出任务持久化到数据库，Redis 作为缓存或队列，而非唯一任务事实来源。
2. 支持任务取消、幂等键、权限隔离、审计记录和告警。
3. 使用消息队列或独立 worker 服务隔离 Web 请求线程与重计算任务。
4. 建立容量告警：队列积压、任务失败率、线程池拒绝、连接池等待、对象存储上传失败和临时文件残留。

## 7. 当前配置决策建议

- 默认导入 worker 不宜直接使用压测最快的 16。应先保证 `HIKARI_MAXIMUM_POOL_SIZE` 有足够余量，并完成多轮复测。
- 若导入与导出会同时发生，导出线程池不宜无约束增大。导入 8 worker、连接池 10 时，两个并发导出任务可能让连接池没有余量。
- `EXPORT_AWAIT_TERMINATION_SECONDS` 是停机收尾等待，不是单个导出任务超时。
- `IMPORT_WORKER_FINISH_WAIT_SECONDS=0` 表示接口等待所有 worker 自然结束；若设置正数，必须覆盖单批事务和全部重试退避窗口。

## 8. 结语

这个项目的优化过程证明，大文件导入导出不是单纯替换一个 Excel 库或增加几个线程。可靠方案需要同时处理流式内存边界、数据库事务、并发容量、任务状态、对象存储、失败收尾、可观测性和安全配置。

下一步最值得投入的是可重复压测和任务可恢复性。前者用于确定真实最优参数，后者决定系统在失败、重试和大规模业务使用下是否真正可运营。
