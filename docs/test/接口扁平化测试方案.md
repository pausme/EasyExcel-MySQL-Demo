# 接口扁平化测试方案

## 1. 测试目标

以**测试工程师视角**，对本系统全部 HTTP 接口进行**扁平化测试（Flat Interface Testing）**：

- **扁平化**：不依赖 UI 或单一端到端长链路，而是对**每个接口逐个直接发起请求**，独立验证其行为；
- **全流程**：覆盖正常主流程（happy path）的完整业务闭环；
- **全封闭**：每个接口覆盖其全部分支——正常、边界、异常、业务规则与归属/权限，形成可追溯、可复核的测试记录。

最终产出一份“用例矩阵 + 真实执行记录”双交付物，既可作为回归基线，也可暴露接口层的实现缺陷。

## 2. 测试范围

系统共 **4 个模块、32 个接口**：

| 模块 | 基础路径 | 接口数 | 说明 |
| --- | --- | ---: | --- |
| Excel 导入导出 | `/api/excel` | 9 | 学生总数、造数、异步导入/导出、模板、错误明细下载 |
| 异步任务中心 | `/api/tasks` | 4 | 任务详情、分页、取消、重试 |
| 报表运行控制 | `/api/report/student-runs` | 7 | 运行控制 CRUD、运行生成导出、历史任务 |
| 文件上传中心 | `/api/files` | 12 | 后端上传、秒传、直传、分片上传、详情/下载/删除/分页 |

归属机制：通过请求头 `X-User-Id` 区分任务归属，未传时取默认 `anonymous`；越权访问统一返回 `404`，不泄露资源存在性。

完整接口清单与参数说明见 [`接口扁平化测试用例.xlsx`](接口扁平化测试用例.xlsx) 的“接口参数列表”工作表。

## 3. 测试策略

### 3.1 扁平化用例设计原则

每个接口至少覆盖以下五类场景（视接口复杂度裁剪）：

1. **正常（Positive）**：合法入参的主流程，验证成功返回与业务结果；
2. **边界（Boundary）**：分页缺省/越界、数值上下限（年龄 0–150、分片 ≥5MB、分片数 ≤1000、文本长度截断、MD5 32 位）；
3. **异常（Exception/Negative）**：缺参、空值、格式非法、资源不存在（404）、非法状态机迁移（409）；
4. **业务规则（Business Rule）**：唯一性约束（运行控制编码）、原子性（重复学号导入回滚）、秒传命中/未命中、取消/重试状态机、逻辑删除后不可见；
5. **归属/权限（Ownership）**：跨用户访问他人资源一律 `404`。

### 3.2 用例分级

| 优先级 | 含义 | 颜色 |
| --- | --- | --- |
| **P0** | 冒烟/主流程，必须通过 | 红 |
| **P1** | 重要分支与异常路径 | 黄 |
| **P2** | 边界与补充场景 | 绿 |

### 3.3 异步任务处理

导入/导出/报表运行均为异步任务：提交接口仅返回 `taskId`，需**轮询状态接口**直至 `SUCCESS`/`FAILED` 再断言最终结果，避免把“提交成功”误判为“业务成功”。

## 4. 测试环境

### 4.1 被测应用

- Spring Boot 2.6.13（fat jar：`target/demo-0.0.1-SNAPSHOT.jar`），监听 `SERVER_PORT`；
- 依赖中间件：MySQL、Redis、MinIO（均为远程实例）；
- 关键配置：导入 16 worker / 单任务并发 / 2000 行每批；导出 2 核 2 最大线程、队列 10、拒绝策略 `abort`；分片最小 5MB、最大 1000 片；签名下载有效期 30 分钟。

### 4.2 单元/切片测试（无需中间件）

项目自带 9 个测试类 / 33 个 `@Test`。`DemoApplicationTests` 使用 H2（MySQL 模式）+ `test-redis.invalid` / `test-minio.invalid` 桩地址、关闭建表初始化来加载上下文，因此**无需真实中间件即可运行**。

执行：`mvn test`

### 4.3 接口联调测试（需真实中间件）

启动应用并使用真实环境参数后，由 [`scripts/run_flat_tests.py`](../../scripts/run_flat_tests.py) 逐接口发起真实 HTTP 请求并记录实际状态码与响应。脚本会：

- 自动生成测试夹具（合法导入 Excel、直传/分片用的二进制文件，并计算真实 MD5）；
- 对直传/分片上传，先 PUT 到 MinIO 预签名地址再调用完成接口，验证完整闭环；
- 对异步任务轮询至终态；
- 将结构化结果写入 [`live-test-results.json`](live-test-results.json)。

## 5. 通过准则

- P0 用例 100% 通过；
- P1 用例通过率 ≥ 95%；
- 所有“失败”与“待确认（CHECK）”用例需在 [`测试执行记录.md`](测试执行记录.md) 中给出原因与处置建议；
- 发现的接口缺陷（如缺少全局异常处理导致 500）单列“问题与风险”章节跟踪。
